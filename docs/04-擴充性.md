# 擴充性

## 1. 網站真正的工作

這個網站不只是 Landing Page。依 vision 的 Principle「先成立媒體，再請求幫助」，網站本身就是組織的**媒體**與**知識介面**。它的長期工作有六項：

| # | 工作 | 服務對象 | 現在 | 未來 |
|---|---|---|---|---|
| J1 | 說清楚我們是誰 | 所有人 | 首頁、關於 | 英文版、媒體素材包 |
| J2 | 讓人加入 | 探索者、founder | 加入流程 | 自介產生器、新人導覽 |
| J3 | 找到人 | 成員、發起活動的人 | — | 成員目錄、R&R 搜尋、（Note）配對 |
| J4 | 找到知識 | founder | — | 攻略與流派、搜尋、依情境推薦閱讀路徑 |
| J5 | **讓前輩看見效益** | 矽谷前輩、VC | — | 前輩分享／AMA 紀錄、影響力數據 |
| J6 | 讓 AI 讀得懂 | 使用 AI 的成員 | `llms.txt` | 內容 API、（Note）MCP／Agent Skills |

前一版規劃少了 **J5**。vision 寫到前輩「對能否帶來改變有所懷疑」，請他們幫忙時「需要讓他們看見時間能帶來什麼效益」。所以網站之後需要：

- **分享紀錄**：一場交流整理成什麼筆記、署名誰（例如「想問矽谷大佬關於創業出海的問題」活動的成果頁）。
- **影響力數據**：筆記數、貢獻者數、成員數、閱讀量，以及一次分享被多少人參考。

## 3. 現在就要做對的決定（之後改很貴）

| # | 決定 | 為什麼現在做 | 成本 |
|---|---|---|---|
| E1 | **內容圖譜與公開 JSON API** `src/graph/` → `/api/v1/*.json` | 網站、`llms.txt`、未來的 MCP server、Discord bot 都讀同一份資料；`src/graph/` 不依賴 Astro，需要時可搬成套件 | 低 |
| E2 | **統一身分鍵：GitHub 帳號** | 成員、筆記作者、貢獻者、衍生專案維護者都能用同一個鍵串起來；之後要對應 Discord 也從這裡接 | 低 |
| E3 | **i18n 路由從第一天就開** | 之後再把網址改成 `/en/` 會破壞既有連結和 SEO；英文內容可以晚點補 | 低 |
| E4 | **穩定的永久網址** `/members/<github>`、`/notes/<slug>` | 筆記會被 Discord、Threads、AI 引用，網址不能變 | 零 |
| E5 | **內容型別用 Zod schema 定義，分類維度寫成設定檔** | 流派維度（Founder-Market Fit、團隊組合、產業）還在演進；加新維度只改設定、不改程式 | 低 |
| E6 | **選可以混合渲染的框架與託管** | Astro + Cloudflare 可以在單一路由加上伺服器端功能（Workers、D1、KV），整站不必重寫 | 零（選型已涵蓋） |
| E7 | **設計 token** `src/styles/tokens.css` | Sun 的設計集中在一處，跨頁面重用 | 低 |

## 4. 刻意不做（YAGNI）

- 不做登入、資料庫、CMS：成員是志工、組織沒有資金，每多一個服務就多一份維運與費用。
- 不做配對、報名、mentor：都還在 Note，沒在 mono 拍板就不實作（也不能在網站上宣稱）。
- 不做微服務、不拆多個部署：一個 Astro 站加上需要時的 Workers 就夠了。

## 5. 加入動態功能的路徑（等有需求時）

1. 先在 mono 拍板，寫成 `[機制]`／`[功能]` 規格並通過憲法檢查。
2. Astro 對該路由啟用 server 輸出（Cloudflare adapter），其他頁維持靜態。
3. 資料先用 Cloudflare D1／KV（免費額度），需要身分時優先用 GitHub OAuth（與 E2 一致）。
4. 再複雜才考慮把 `apps/api` 拆成獨立 Worker。
