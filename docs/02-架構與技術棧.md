# 架構與技術棧（v2，重新設計）

## 0. 這版改了什麼

| 項目 | v1 | v2 | 理由 |
|---|---|---|---|
| 核心抽象 | 頁面讀 Markdown | **內容圖譜（Content Graph）**：人、文件、筆記、活動、貢獻，用 GitHub 帳號串起來 | credits、成員目錄、知識庫、配對都是同一張圖的不同視角 |
| 擴充方式 | pnpm workspace 拆 `packages/*` | **單一 Astro app＋公開的靜態 JSON API** | 未來的 bot、MCP、配對工具讀部署好的 JSON 就好，不必共用程式碼；只有出現第二個程式消費者時才拆套件 |
| Credits | 頁尾名單 | **從 git 歷史逐檔計算**＋`credits.yml` 補非程式貢獻 | W4：讓大家的 credits 被看見 |
| 文案編輯 | 改 Markdown 開 PR | V1 同上＋PR 預覽；M2 視需要加 **Keystatic** 視覺化編輯 | W2：大家再一起修文案，非工程師也能改 |
| 託管 | Cloudflare Pages | **Cloudflare Workers（Static Assets）** | Cloudflare 已把 Pages 併入 Workers；之後要加動態路由不必搬家 |

## 2. 內容圖譜

| 實體 | 來源 | 關鍵欄位 |
|---|---|---|
| `Person` | Members 自介、git 作者、`credits.yml` | `github`（主鍵）、名稱、頭像、我是誰、可以幫什麼忙、想要幫什麼忙、是否有自介 |
| `Document` | mono `specs/` | 路徑、標題、層級（Problem／Principle／機制／功能）、原文、GitHub 連結 |
| `Note` | mono 筆記（M3） | 流派維度、適合誰、成本、標籤 |
| `Event` | web `content/events/` | 標題、日期、地區、連結、發起人 |
| `Contribution` | git log（mono＋web）、資訊貢獻者段落、`credits.yml` | `person` → `target`、類型（code／docs／design／copy／info）、次數、最近日期 |

**由此直接得到的頁面：** `/credits`（依人彙整 Contribution）、每份文件的貢獻者、`/members`（Person＋自介）、之後的配對（比對 Person 的「想找」與「可以幫」）。

**解析原則：**
- 自介格式自由，依標題關鍵字盡量抽出欄位，抽不到就整篇顯示；只發警告，不讓建置失敗。
- 只有已合併進 mono `main` 的自介才會出現；網站標示為「自介」，等審查制度定案後再決定是否改稱「成員」。
- git 作者轉 GitHub 帳號：先看 noreply email，對不到再查 GitHub API，結果快取。

### 為什麼不是 Next.js

前端志工可能更熟 Next.js，但這個網站 95% 是內容。Next.js 在 Cloudflare 上要透過 OpenNext 轉接，靜態輸出又會失去它的優勢。Astro 的 React Islands 讓大家照樣寫 React，只是寫在需要互動的地方。如果之後真的出現大量登入、即時互動的功能（例如配對系統），再把它做成獨立 app，讀同一份 `/api/v1` JSON。

## 4. 公開 JSON API（擴充的接口）

建置時一起輸出，任何人、任何工具都能讀：

| 端點 | 內容 |
|---|---|
| `/api/v1/people.json` | 有自介者的公開欄位（自介裡本人寫的內容） |
| `/api/v1/documents.json` | 組織文件索引 |
| `/api/v1/contributions.json` | 貢獻彙整 |
| `/api/v1/events.json` | 活動 |
| `/llms.txt`、`/llms-full.txt` | 給 AI 的站點摘要與全文（可直接貼給 AI 問「誰能幫這個忙」） |

未來的 Discord bot、MCP server、配對工具都從這裡讀；有版本號，欄位改動不破壞舊的使用者。

## 6. 開發與協作流程

1. **改文案**：在 GitHub 網頁編輯 `src/content/zh/*.md` → 開 PR → 自動出現預覽網址 → 大家在預覽上留言。
2. **改程式**：本機 `pnpm dev`；第一次執行時自動淺複製 mono 到 `.cache/mono`，或用 `MONO_PATH` 指向本機的 mono。
3. **mono 更新**：mono 的 Action 在 push 到 `main` 時送 `repository_dispatch` → web 重建。需要在 mono 加一個 workflow（A7 品毅的 Repo SOP 範圍）。
4. **每日排程**：更新頭像、貢獻統計。
5. **上線前**：CI 全綠、Lighthouse 達標、以 subagent 做憲法逐條檢查。

## 7. 規格放哪裡

依 mono 的 AGENTS.md，規則一律寫在 specs、Plan 用引用聚合。建議網站的 `[功能]` 規格與 Plan 放在 mono（例如新增 `specs/04-網站/`、`plans/00X-Landing-Page/`），web repo 只放程式碼與本 `docs/` 的工程筆記。這需要團隊同意，屬於新的 Plan 範圍。

## 8. 風險

| 風險 | 對策 |
|---|---|
| 自介格式自由、解析失敗 | 寬鬆解析＋整篇顯示；Vitest 用真實自介當測試案例 |
| git 作者對不到 GitHub 帳號 | noreply email → GitHub API → `credits.yml` 手動補 |
| 第二波招募湧入大量 PR，頻繁觸發重建 | 合併 mono 觸發（concurrency 取消舊的建置）；Workers Builds 免費額度足夠 |
| 成員頁暴露個資 | 只顯示本人在 PR 中公開的內容；刪檔即下架 |
| 網站寫出未採納的構想 | 文案 PR 範本附檢查清單；上線前憲法逐條檢查 |
| Keystatic 需要 GitHub App 與伺服器路由 | V1 不導入；等確定有非工程師需要再加 |
